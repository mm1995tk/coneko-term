# coneko-term

**coneko-term is a separate project from kitty.** It aims to implement all 14 items of kitty's [protocol extensions](https://sw.kovidgoyal.net/kitty/protocol-extensions/), but it is not made by or affiliated with kitty.

coneko-term is a library of terminal building blocks. The first user is the GUI of [shijimi-editor](https://github.com/mm1995tk/shijimi-editor), where it replaces xterm.js 6.0.0.

- The VT processing and the screen (parser, cells, cursor, scrollback) are written in Rust and compiled to WebAssembly.
- Drawing is TypeScript on Canvas 2D. Glyphs are drawn with the browser's fonts.
- The Rust core does not depend on the browser, so a native GPU renderer (wgpu and so on) can use the same core later.

The first goal is that shijimi-editor's GUI works with coneko-term as it does with xterm.js. kitty's protocol comes after that. "The same as xterm.js" is measured against the [xterm.js 6.0.0 feature table](https://xtermjs.org/docs/api/vtfeatures/) and its source.

**Status:** the WASM and TypeScript API (`Terminal`) and Canvas 2D drawing (with `fit()` and a scrollbar) are in place. Mouse reporting, the wheel, and selection with copy are in place. The kitty keyboard protocol is partly in place: the mode flags (`CSI > u`, `CSI < u`, `CSI = u`, `CSI ? u`) and all five encoding flags (1 disambiguate escape codes, 2 report event types, 4 report alternate keys, 8 report all keys as escape codes, 16 report associated text). Not done: the lock modifiers (Caps Lock and Num Lock bits), Hyper and Meta, and media keys. The core receives images sent with the kitty graphics protocol (APC `a=t`, `a=T` and `a=q`, chunked, direct transmission only), keeps them, places them on the cells (`a=p`, `a=T`) and deletes them (`a=d`), and lists the placements for the renderer. The renderer draws them on the Canvas: `f=24`, `f=32` and `f=100`, with or without `o=z` (PNG and zlib are decoded in the browser with `createImageBitmap` and `DecompressionStream`; an image that cannot be decoded is not drawn). With `z` below 0 they go under the text, and with `z` below -1073741824 under the cell background colors. Unicode placeholders (`U=1` virtual placements and U+10EEEE, with the row and column diacritics) are drawn too, including the rules for omitted diacritics. Animation is in place: the core keeps the frames (`a=f`, with `x`/`y`/`s`/`v`, the base frame `c`, the edited frame `r`, `X`, `Y` and the gap `z`), the playback state (`a=a`: `s` stop/wait/run, `c` current frame, `v` loops, `r` and `z` gaps) and frame composition (`a=c`), and the renderer composes the frames in the browser and switches them on `requestAnimationFrame` after each frame's gap. The core has no clock. Frame data counts toward the same storage quota as images. Not done: deleting only the frames (`a=d` with `d=f`). Desktop notifications (kitty OSC 99) are read and become events (`onNotification`, with chunked `d=0` notifications joined into one); the replies (clicked, closed, answers to `p=?` and `p=alive`) are written back by methods on `Terminal`. Showing the notification on the OS is up to the application; icon images are not read. The kitty clipboard protocol (OSC 5522) is read and becomes events: a write is joined into one `onClipboardWrite` event (MIME types, chunked base64, aliases, main clipboard or primary selection), and a read request becomes `onClipboardRead`. The application decides whether to allow it and answers with `replyClipboardWrite`, `replyClipboardReadTypes`, `replyClipboardReadData` or `replyClipboardReadError`; with no listener, coneko-term answers "not permitted" (`EPERM`). Connecting to the OS clipboard is up to the application. Paste events (`CSI ? 5522 h`) and the `name` and `pw` keys are not handled; OSC 52 is not done. The kitty drag and drop protocol (OSC 72) is read and becomes events: `onDnd` reports when the program accepts drops, its answers to a drag, the requests for the dropped data and the end of the drop, and when the program offers a drag (MIME types, data sent ahead, drag images), including the remote-machine forms (`text/uri-list` entries, symlinks and directory handles). The application feeds in OS drops with `dropMove`, `dropDrop` and `dropLeave`, answers the data requests with `replyDropData` or `replyDropError`, reports a drag gesture with `dragGesture`, and reports a started drag's progress with `dragStarted`, `dragError`, `dragAccepted`, `dragAction`, `dragDropped`, `dragFinished`, `requestDragData` and `requestDragEntry`; coneko-term builds the escape codes (chunking, the support query, requests refused before the drop or out of range). With no listener, coneko-term answers "not permitted" (`EPERM`). Connecting to the OS drag and drop, and reading and writing files, are up to the application. Computing and comparing the machine id (HMAC-SHA256) is also up to the application. The kitty text sizing protocol (OSC 66) is in place: `s`, `w`, `n`/`d` and `v`/`h` are read, and a character that spans several cells (`w * s` wide, `s` tall, growing right and down from the cursor) is kept in the screen model and drawn on the Canvas by its size and alignment. Overwriting or erasing any part of it removes the whole character, as the spec says. A value out of range, or text over 4096 bytes or with control characters, discards the whole sequence. When the number of columns changes, such characters go back to normal-sized text. The cells exported to TypeScript are now 7 values each (`CELL_STRIDE`), and the new one marks these cells (`RowView.sized`). Not done: adding a combining character to a character that is already placed (it is dropped). The kitty file transfer protocol (OSC 5113) is read and becomes events (`onFileTransfer`): the start of a session (`send` and `receive`), file metadata and path requests, chunked data, the compression mark (`zip=zlib`), the end, and cancel. The application decides whether to allow it and answers with `replyFileTransferOk`, `replyFileTransferStarted`, `replyFileTransferProgress`, `replyFileTransferError`, `refuseFileTransfer` or `replyFileTransferCanceled`, and sends the listing and the data of a receive session with `replyFileTransferListing` and `replyFileTransferData`; coneko-term builds the escape codes (4096-byte chunks, leaving replies out for `q`). With no listener, coneko-term refuses `send` and `receive` ("not permitted", `EPERM`) and answers a cancel with `CANCELED`. Reading and writing files, checking paths, compressing and decompressing data, making and reading rsync signatures and deltas, and checking `pw` are up to the application. The kitty multiple cursors protocol (`CSI > ... SP q`) is in place: extra cursors are added, cleared and queried (by point, by rectangle or at the main cursor), with the shape (block, bar, underline or following the main cursor) and the shared cursor and text color pair (`CSI > 30` and `CSI > 40`), and the Canvas renderer draws them. They are kept in the screen model (`Screen::extra_cursors`, `Terminal.extraCursors`), apart from the main cursor. `CSI 2 J`, `CSI 3 J`, `CSI 22 J`, RIS and switching between the main and alternate screens remove them; scrolling does not move them. A resize drops the ones that fall outside the new screen. They blink like the main cursor and stay visible when the main cursor is hidden. The kitty mouse pointer shapes (OSC 22) are in place: setting, pushing, popping and querying (`?`, including `__current__`, `__default__` and `__grabbed__`) follow the spec, with separate stacks for the main and alternate screens, and the shape names are the CSS `cursor` values. `Terminal.pointerShape` gives the current shape, and the element made by `open` gets it as its `cursor` style, whether mouse reporting is on or not. Not done: the old xterm shape names (aliases). The kitty unscrolling extension (`CSI n + T`) is in place: it moves the screen down by n lines and fills the freed lines at the top from the end of the scrollback, with their attributes. Lines the scrollback does not have are left blank. On the alternate screen, which has no scrollback, it is the same as `CSI n T`. With a scroll region, it works inside the region, and the lines come from the scrollback of the main screen. The rectangular attribute change (DECCARA and DECRARA) is in place: `CSI Pt;Pl;Pb;Pr;Ps$ r` sets attributes and `CSI Pt;Pl;Pb;Pr;Ps$ t` reverses them. As in the kitty extension, DECCARA takes all of SGR (256 and RGB colors, and the underline style and color). DECRARA reverses bold, dim, italic, underline, blink, inverse, invisible and strikethrough, and does not reverse colors (`0` and no parameter mean the DEC four: bold, underline, blink and inverse). DECSACE (`CSI Ps * x`) chooses the extent: `2` is a rectangle, and `0`, `1` or no parameter is the stream of lines (the default). In origin mode (DECOM) the position counts from the top left of the scroll region, and a bottom edge past the region is clamped to its last line. Left and right margins (DECLRMM) are not supported. kitty color control (OSC 21) is in place: every key in the spec (`foreground`, `background`, `selection_background`, `selection_foreground`, `cursor`, `cursor_text`, `visual_bell`, `transparent_background_color1` to `7`, and 0 to 255 for the color table) can be read (`key=?`), set (`key=color`), made dynamic (`key=`) and reset to the default (the key alone), and the reply has the spec's form (`rgb:rr/gg/bb`, empty for an undefined color, `unknown=` plus unpadded base64 for an unknown key). Colors are written as `rgb:`, `#`, `rgbi:` or a name; the opacity after `@` is read and dropped, and only a short list of X11 color names is known (red, green, blue, and a few more). A value that cannot be read is dropped. OSC 4, 10, 11 and 12 now set colors too (and OSC 104, 110, 111 and 112 reset them), on the same color table as OSC 21, so either can read what the other wrote. The renderer draws the changed foreground, background, cursor, cursor text, selection background and the color table; `Terminal` checks for changes after each `write`. The core exposes them as `Terminal::colors`. Not drawn: `selection_foreground`, `visual_bell` and the transparent background colors (they are kept and can be read), and the selection background keeps the translucency of `theme.selectionBackground` (alpha `4d` when set by OSC 21) so the text stays visible. The color stack is in place: `CSI # P` (XTPUSHCOLORS), `CSI # Q` (XTPOPCOLORS) and `CSI # R` (XTREPORTCOLORS, answered with `CSI Pi ; Pn # Q`), with 10 slots, plus OSC 30001 and OSC 30101. RIS puts the colors back to the theme and empties the stack. The small extensions in kitty's miscellaneous protocol are in place. `CSI ? s` and `CSI ? r` save and restore terminal modes: with a list of modes (XTSAVE and XTRESTORE) only those, and with no list (the kitty extension) all the modes that have no side effects (so not DECOM and not the modes that switch screens). `CSI 221 m` and `CSI 222 m` reset bold and faint separately (`CSI 22 m` still resets both). When mouse reporting is `CSI ? 1003 h` with `CSI ? 1016 h` (SGR pixels), the element made by `open` reports the mouse leaving the window as `CSI < 163 ; 0 ; 0 M` (`Terminal.handleMouse` with `type: "leave"`; it is not reported while a button is held). `CSI 22 J` moves the text and the images of the screen into the scrollback and leaves the screen as `CSI 2 J` does; it moves only down to the last line that has something, so it adds no blank lines, and on the alternate screen it only clears. The Program Status Protocol (OSC 7501, revision 0.4) is read and becomes events (`onProgramStatus`), and `Terminal.programStatus` lists the records: the states (idle, working, done, blocked, error), `kind`, `progress`, `app` (inherited from the nearest parent), `title` and `msg`, the ids and `state=clear`, the limits (a report that breaks one is discarded whole), and the feature detection reply. The records go away on RIS, `state=clear`, a new shell prompt (OSC 133 `A`; working, blocked and idle), the window gaining focus or a key press (done and error), and when the application calls `programStatusProcessExited` (working, blocked and idle). The records are not a GUI: what to show is up to the application. A malformed `id` makes the whole report ignored, so that it cannot overwrite the root record. Not done: mapping OSC 9;4 to the records. The section "kitty specific private escape codes" is not done.

## Packages

- crate `coneko-term` (`coneko_term` in code): the core, in `crates/coneko-term`.
- npm package `coneko-term`: the WASM and the TypeScript types. The built `.wasm` is in the package, so it works with `npm --ignore-scripts`.

```ts
import { init, Terminal } from "coneko-term";

await init();
const term = new Terminal({ cols: 80, rows: 24, scrollback: 1000 });
term.onData((bytes) => pty.write(bytes)); // replies (DSR and so on) and input() go out here
term.registerOscHandler(133, (data) => console.log("OSC 133", data));
term.write("hello\r\n", () => console.log("processed"));
```

`Terminal` has no DOM dependency until you call `open(host)`. Large `write`s are processed in small slices, and `done` is called when that data has been processed. `takeDirtyRows()` and `readRow(y)` give the changed rows as cells in WASM memory.

## Saving the screen state (Rust crate)

`Terminal::serialize(max_scrollback)` in the crate returns bytes that, written to a new `Terminal` of the same size, give the same screen. It is the same idea as xterm.js's `SerializeAddon`: a server can keep a headless `Terminal`, and a client that connects later gets the state instead of a replay of the old output (a replay answers old queries such as DECRQM a second time, and the answers reach the shell as input).

```rust
let bytes = term.serialize(5000); // the newest 5000 scrollback rows
let mut other = coneko_term::Terminal::new(rows, cols);
other.write(&bytes);
assert!(other.take_output().is_empty()); // the bytes contain no queries
```

Included: the visible screen and the newest `max_scrollback` rows of the main screen (characters, SGR attributes, wrapped lines); whether the alternate screen is shown (the main screen is saved too); the cursor (position, pending wrap, shape, blinking, visibility), the DECSC-saved cursor, the scroll region and the tab stops; the kitty keyboard flag stacks of both screens; DEC modes (mouse reporting, bracketed paste, focus reports, DECCKM, DECOM, auto-wrap and the others), IRM and LNM; foreground, background, cursor and palette colors that differ from the `Theme` (both terminals must use the same theme).

Not included: kitty graphics images and their placements, character sets (G0 to G3), modes saved with `CSI ? s`, extra cursors, the color stack, colors only OSC 21 changes, the title, and the half-finished state of notifications, clipboard, drag and drop and file transfer. The wrapped flag of the last scrollback row is not kept, and OSC 66 text taller than one row is not written inside the scrollback. The npm package does not expose this yet.

## Drawing

```ts
const term = new Terminal({ fontFamily: "'JetBrains Mono', monospace", fontSize: 15, lineHeight: 1 });
await document.fonts.load("15px 'JetBrains Mono'"); // optional: the cell size is measured again when fonts finish loading
term.open(pane); // creates an element with a canvas, a scrollbar and a hidden textarea (it takes the focus)
term.fit(); // cols and rows from the size of `pane` (minus the scrollbar width, as xterm.js's FitAddon)
term.onCellSizeChange(() => term.fit()); // fonts loaded, devicePixelRatio changed
```

The scrollbar is 14 CSS pixels wide by default. Pass `scrollbarWidth` to `new Terminal({ ... })` to change it (for example `scrollbarWidth: 8`); `fit()` subtracts that width. `scrollbarWidth: 0` shows no scrollbar and subtracts nothing. A negative or non-numeric value falls back to 14.

URLs on screen: `http://` and `https://` URLs (also ones wrapped over several rows; text up to the first space, non-ASCII character or URL-unsafe symbol, minus trailing `.,;:!?*` and unmatched closing brackets) get an undercurl. Turn it off with `underlineUrls: false` (or `term.underlineUrls = false` later). `term.onUrlClick(({ url, shiftKey, altKey, ctrlKey, metaKey }) => ...)` fires when the left button is pressed and released on the same cell of a URL (not after a drag); opening the URL is up to the listener. With mouse reporting on, hold Shift (the same as selecting). Pass `metaKey: e.metaKey` in `handleMouse` if you call it yourself. `term.getVisibleUrls()` returns the visible URLs as `{ url, segments: [{ row, startCol, endCol }] }` (`endCol` is exclusive; a wrapped URL has one segment per row). Lines the shell is taking input on (the prompt and the command being typed, from OSC 133 `A` or `B` to `C` or `D`; `RowView.input`) get no undercurl, and are not clicked or listed; a shell that sends no OSC 133 gets undercurls on every line as before. A shell that sends `A` and `D` but never `C` cannot tell where the output begins, so its output lines are treated as input lines too (no undercurl); send `C` (the start of the output) to avoid this. While Cmd (`metaKey`) is held over a URL that a click would open, `term.hoveringUrl` is true and the element made by `open` gets `cursor: pointer` (this wins over OSC 22); if you do not use `open`, read `hoveringUrl` after each `handleMouse`. OSC 8 hyperlinks are not supported.

Drawing uses Canvas 2D with the browser's fonts (fallback fonts work for CJK), is crisp at any `devicePixelRatio`, and is batched with `requestAnimationFrame`: only changed rows are redrawn. `viewportY`, `scrollLines(n)`, `scrollToTop()`, `scrollToBottom()`, `scrollToLine(n)` and `onScroll` move the viewport into the scrollback; at the bottom it follows new output. Try it with `npm run build && node demo/serve.mjs` (open `/demo/`).

## Mouse and selection

`open()` binds the mouse for you. When the app asks for mouse reporting (modes 9, 1000, 1002, 1003 with the default, SGR 1006 or SGR-pixels 1016 encoding), presses, releases, motion and the wheel go out through `onData` (the wheel sends one report per line scrolled; a move of less than a line sends none and carries over to the next), the same way as xterm.js 6.0.0 (the default encoding drops positions beyond column or row 223; 1005 and 1015 are treated as the default encoding, as xterm.js does not support them). Holding Shift forces selection instead. Without reporting, the wheel moves the viewport; on the alternate screen it sends Up/Down arrow keys. Drag selects a range, double click a word (`wordSeparator` option), triple click a line; wrapped lines are joined without a newline. `getSelection()`, `hasSelection()`, `getSelectionRange()`, `selectAll()`, `clearSelection()` and `onSelectionChange` are available, and the element answers the `copy` event with the selection (as xterm.js does). The selection color is `theme.selectionBackground`. Without a DOM, call `handleMouse()` and `handleWheel()` yourself.

## Keyboard, IME and paste

`open(host)` puts a hidden `textarea` in the element; `focus()` focuses it. Keys, IME text and pastes go out through `onData`, the same outlet as the replies. The bytes for keys are the same as xterm.js 6.0.0 (`evaluateKeyboardEvent` is exported and is a port of its `Keyboard.ts`):

- Enter, Backspace, Tab, Shift+Tab, Esc, arrows (`CSI` or `SS3` by DECCKM), Home, End, PageUp, PageDown, Insert, Delete, F1 to F12, modifiers (`CSI 1;m X`), Ctrl+letter, Alt as an ESC prefix. Shift+PageUp and Shift+PageDown scroll the viewport.
- On macOS, Option types a character (`macOptionIsMeta: false`, as xterm.js); set `macOptionIsMeta: true` to send ESC-prefixed keys. Keys with Cmd are not sent (left to the app's shortcuts).
- IME: nothing is sent while converting; the confirmed text is sent. The text being converted is shown at the cursor.
- `paste` events are handled; `term.paste(text)` does the same. Newlines become `\r`; with bracketed paste (2004) the text is wrapped in `ESC [200~` and `ESC [201~`.
- With focus reporting (1004), `CSI I` and `CSI O` are sent when the `textarea` gains and loses focus.
- With the kitty keyboard protocol on (flags set by the app), keys go out as `CSI ... u` as the spec says. `KeyHandler` also listens to `keyup` for flag 2: a release is sent only for a key whose press it sent as an escape code, so the Enter that ends an IME conversion does not produce a stray release. While converting, nothing changes: no escape codes, and the confirmed text is sent as plain text. Where the key is on the layout (flag 4) comes from `KeyboardEvent.code`, assuming a US PC-101 base layout.
- `attachCustomKeyEventHandler(fn)` sees key events first; return `false` to skip a key. `scrollOnUserInput` (default true) returns to the bottom when you type.

## Development

Everything runs in the Nix devShell (Rust with the `wasm32-unknown-unknown` target, wasm-bindgen, Node.js).

```sh
nix develop          # or: direnv allow
cargo test           # Rust tests
npm ci --ignore-scripts && npm run build && npm test   # WASM, package, TypeScript tests
nix fmt              # format
nix flake check      # formatting, cargo test, npm package build and tests (what CI runs)
nix build .#npm      # the npm tarball, with the .wasm and the .d.ts
```

See [AGENTS.md](AGENTS.md) for the rules. For publishing to crates.io and npm, see [RELEASING.md](RELEASING.md).
